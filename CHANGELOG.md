Did a manual line-by-line self-review of all 15 Kotlin files and every Gradle/XML file (no compiler available in this sandbox, same restriction as the sixth revision — this was static review, not a build). Found one build-breaking bug and six real gaps; fixed all seven, verified XML well-formedness and brace balance again post-fix, re-synced the scratch and project copies (`diff -rq` confirms identical).
- **Fixed (build-breaking):** `app/build.gradle.kts` paired Kotlin 2.0.20 with `composeOptions.kotlinCompilerExtensionVersion = "1.5.14"` — that versioning scheme was retired in Kotlin 2.0 in favor of a dedicated Gradle plugin; as written, Gradle sync would have failed outright. Added `id("org.jetbrains.kotlin.plugin.compose") version "2.0.20"` in both `build.gradle.kts` (root, `apply false`) and `app/build.gradle.kts`; removed the obsolete `composeOptions` block.
- **Fixed (functional bug):** `notifications/ReminderScheduler.kt` used `ExistingPeriodicWorkPolicy.UPDATE` when rescheduling — that policy preserves the already-scheduled next run time and does not honor a new initial delay on an update, so changing the reminder time in Settings could silently fail to move the next fire time. Switched to `ExistingPeriodicWorkPolicy.REPLACE` (deprecated for the general case, but the one policy that actually cancels-and-re-enqueues fresh, which is what "user changed the time" needs).
- **Fixed (data-correctness bug):** `ui/CheckInViewModel.kt` computed "today's date" in the device's local timezone; the backend's canonical timezone (`backend/src/db.js`'s `config.timezone` default) is `Asia/Kolkata`. Travel outside IST could log a check-in under the wrong calendar date around midnight. Fixed to compute the date explicitly in `Asia/Kolkata` regardless of device locale/timezone.
- **Fixed (dead code / broken UX):** `ui/SettingsScreen.kt` had no back-navigation affordance, and Save immediately called `onBack()` before the `savedConfirmation` flag it set could ever render — the confirmation state was unreachable dead code. Added a back button in the top bar, stopped auto-navigating on save, and now actually show a "Saved." confirmation (cleared again on any subsequent edit).
- **Fixed (undocumented failure mode):** Release builds block all cleartext HTTP outright (`network_security_config.xml`) with nothing in the app explaining why a `http://` backend URL just silently fails. Added an inline warning in Settings when the URL starts with `http://`.
- **Fixed (asset quality):** `notifications/NotificationHelper.kt` used `android.R.drawable.ic_dialog_info` — a full-color system dialog icon never designed as a status-bar silhouette — as the notification's small icon. Replaced with a proper monochrome vector (`res/drawable/ic_notification.xml`), same "white shape on transparent background" pattern as the launcher icon.
- **Added** `android/.gitignore` — was missing entirely; `backend/.gitignore` already exists per standing project convention, `android/` had no equivalent. Standard Android Studio ignores (`.gradle/`, `local.properties`, `build/`, `*.iml`, `.idea/`, build outputs).
- **Removed** unused `CheckInViewModel.resetState()` — dead code, never called anywhere.
- **Minor cleanup:** `SettingsViewModel.save()` used a fully-qualified `getApplication<android.app.Application>()` instead of the already-imported `Application` type.

- **Fixed (real gap, data exposure):** `app/src/main/AndroidManifest.xml` had `android:allowBackup="true"` with no `dataExtractionRules` exclusion. `PrefsRepository`'s DataStore file holds `API_SHARED_SECRET` in plaintext, and with no exclusion rule that file is eligible for Android's Auto Backup to Google's cloud storage by default - a bearer token for a paid API silently synced to a cloud account isn't a reasonable default for a personal single-user app. Changed to `android:allowBackup="false"`. Trade-off (documented in the manifest comment): reinstalling or moving to a new device means retyping the backend URL and secret once in Settings - trivial next to the alternative.
- **Caught and fixed my own mistake mid-edit:** the first attempt at the above fix placed an XML comment inside the `<application>` tag's attribute list (`android:allowBackup="false" <!-- ... --> android:icon=...`), which is invalid XML - comments can't appear between attributes of a single element. Caught via the same `python3 xml.dom.minidom` verification step used throughout this project, fixed by moving the comment above the `<application>` tag before it was ever synced anywhere.
- **Hardened (not a functional bug, but worth doing):** `.github/workflows/build-apk.yml`'s unquoted `on:` key is valid, standard GitHub Actions syntax - GitHub's own workflow parser handles it correctly, and the vast majority of real-world workflows use it unquoted. It's a known YAML 1.1 pitfall for *other* tools, though: this project's own verification step (`pyyaml`) parsed it as the boolean `true` rather than the string key `"on"` (the classic "Norway problem" - bare `on`/`off`/`yes`/`no` coerce to booleans in YAML 1.1). Quoted it (`"on":`) so no YAML tooling anyone points at this file - linters, editors, or otherwise - hits the same ambiguity. Verified post-fix: `yaml.safe_load` now returns a dict with an `"on"` string key, not a `True` key.
